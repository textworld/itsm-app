# 管理员排班配置列表与详情设计

## 背景

当前 `/schedules` 是管理员排班配置单页，直接在同一个页面编辑所有排班分组。现有配置结构为：

```js
{
  groups: [
    {
      id,
      name,
      systemCodes,
      baseSchedule: { userIds },
      insuranceTeams: [
        { id, name, userIds, insuranceTypeCodes }
      ],
      flexibleRules: [
        {
          id,
          systemCodes,
          assignees: [
            { userId, ratio }
          ]
        }
      ]
    }
  ]
}
```

现有接口 `GET /api/admin/schedules` 和 `PUT /api/admin/schedules` 已提供配置读取、系统选项、启用险种、一线人员列表，以及前后端共用的 `validateScheduleConfig` 校验。本次只调整管理员排班配置的页面组织方式，不新增表，不修改工单状态、派单、受理、子任务或状态机逻辑。

## 目标

- `/schedules` 展示排班规则列表。
- 列表表格展示分组名称、系统范围、相应人员和操作。
- 列表支持按系统和人员搜索。
- 点击编辑进入单个排班规则的详情配置界面。
- 新增排班规则也进入同一套详情配置界面。
- 详情页保留现有排班配置字段和校验能力。
- 详情页支持维护灵活规则，允许针对部分系统配置专门人员和人员级派单比例。

## 非目标

- 不改变排班配置存储结构。
- 不新增后端排班规则单条 CRUD 接口。
- 不接入自动派单或子任务路由。
- 不直接写入工单 `status`、`requesterStatus`、`supportStatus`、`processingSubStatus`。

## 页面结构

### 排班规则列表页

路径：`/schedules`

列表页加载 `GET /api/admin/schedules`，把 `config.groups` 展示为表格。

表格列：

- 分组名称：`group.name`
- 系统范围：把 `group.systemCodes` 映射为系统名称
- 相应人员：展示基础排班人员和险种排班小组人员的汇总名称
- 操作：编辑

搜索区：

- 系统搜索：按系统名称或系统编码匹配
- 人员搜索：按人员姓名、用户名或用户 ID 匹配

交互：

- 点击“新增排班规则”进入新增详情页。
- 点击某一行“编辑”进入该分组详情页。
- 空列表时显示空状态和新增入口。
- 加载失败或接口错误时展示 `Alert`。

### 排班规则详情页

路径：

- 编辑：`/schedules/[groupId]`
- 新增：`/schedules/new`

详情页复用现有编辑能力：

- 分组名称
- 系统范围多选
- 基础排班人员多选
- 险种排班小组列表
- 险种排班小组人员和险种；不再单独维护小组名称
- 新增/删除险种排班小组
- 灵活规则列表
- 灵活规则系统多选、人员多选式比例配置、删除灵活规则

保存流程：

1. 页面加载完整配置和选项。
2. 编辑时通过 `groupId` 找到目标分组；新增时创建本地空白分组。
3. 保存前把当前分组写回 `groups` 数组。
4. 调用 `validateScheduleConfig({ groups }, context)` 做前端校验。
5. 校验通过后调用 `PUT /api/admin/schedules` 整体保存。
6. 保存成功后返回 `/schedules`。

找不到分组时，详情页展示错误提示并提供返回列表入口。

### 灵活规则

灵活规则只作为后台配置保存，暂不接入真实工单派单逻辑。每条规则配置一组系统和一组人员比例：

```js
{
  id: 'flex_...',
  systemCodes: ['ERP_CORE', 'CRM_CENTER'],
  assignees: [
    { userId: 'u_l1_1', ratio: 70 },
    { userId: 'u_l1_2', ratio: 30 }
  ]
}
```

校验规则：

- 每条灵活规则至少选择一个系统。
- 每条灵活规则至少配置一名人员。
- 灵活规则里的系统必须属于当前排班规则的系统范围。
- 同一个排班规则内，多条灵活规则不能覆盖同一个系统。
- 灵活规则人员必须是可选 `L1` 一线人员。
- 同一条灵活规则内人员不能重复。
- 每个人员比例必须是大于 0 的数字。
- 不校验人员比例合计是否等于 100。

## 数据与接口

继续使用现有接口：

- `GET /api/admin/schedules`
- `PUT /api/admin/schedules`

不新增 API。原因是当前配置作为一个整体对象保存，现有后端校验依赖跨分组唯一性，例如一个系统不能出现在多个排班分组中。整体保存能继续复用现有校验路径，避免增加单条更新接口后产生重复的合并和冲突逻辑。

## 组件与工具拆分

建议在 `src/views/AdminScheduleConfig/` 内拆分：

- `index.jsx`：列表页入口
- `ScheduleDetailPage.jsx`：新增/编辑详情页
- `scheduleConfigViewModel.js`：系统、人员摘要和搜索过滤的纯函数

这样列表摘要和搜索可以用纯函数测试覆盖，详情页继续复用现有编辑逻辑，避免把列表筛选逻辑揉进 JSX。

## 权限与导航

沿用现有 `/schedules` 服务端保护逻辑：

- 未登录跳转登录。
- 非管理员显示无权限。
- 管理员可访问列表页。

新增详情页也使用同样的管理员保护逻辑。

## 错误处理

- 加载失败：列表页和详情页显示 `Alert`。
- 前端校验失败：详情页顶部显示结构化错误列表。
- 后端校验失败：详情页顶部显示后端返回的结构化错误列表。
- 保存失败：保持当前编辑状态，不返回列表。
- 分组不存在：显示错误和返回列表按钮。

## 测试策略

- 更新 `src/views/AdminScheduleConfig/__tests__/adminScheduleConfigView.test.js`：
  - 列表页调用 `/api/admin/schedules`
  - 列表页包含系统搜索、人员搜索、表格列和编辑入口
  - 详情页包含现有基础排班和险种排班小组编辑能力
  - 详情页保存使用 `PUT /api/admin/schedules`

- 新增或扩展纯函数测试：
  - 系统名称/编码搜索可以匹配分组
  - 人员姓名/用户名/ID 搜索可以匹配基础排班和险种小组人员
  - 相应人员摘要包含基础排班和险种小组人员

现有服务端配置校验、路由鉴权和存储测试不需要因本次页面拆分改动。

## 风险与取舍

- 继续整体保存配置，能复用现有跨分组校验，但两个管理员同时编辑时仍以后保存者为准；这和当前页面行为一致。
- 新增详情页在保存前只存在于本地状态，用户返回列表不产生空分组，避免脏数据。
- 页面拆分后详情页需要根据完整配置定位单个分组，因此保存仍会携带全部 `groups`。
