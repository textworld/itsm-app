# 工单详情页右侧快速留言设计

## 背景

当前工单详情页左侧已经提供完整留言板，支持历史浏览、引用回复、富文本和附件上传。右侧区域目前仅承载按角色展示的操作卡片。

本次目标是在不打乱现有详情页结构的前提下，在右侧增加一个“快速留言”入口，方便用户在处理工单时直接补充留言，同时保持左侧留言板作为完整记录的主展示区域。

## 目标

- 在工单详情页右侧新增一个轻量的“快速留言”卡片。
- 保持角色操作区在上、快速留言卡片在下。
- 支持文本留言和附件上传。
- 发送后继续停留在右侧，便于连续留言。
- 提供“查看全部留言”入口，将用户引导到左侧完整留言区。
- 不新增新的消息数据结构，继续复用现有 `ticket.messages`。

## 非目标

- 不在右侧展示完整留言历史。
- 不在右侧支持引用回复。
- 不对左侧完整留言板做大规模重构。
- 不改动消息存储模型与上下文接口。

## 方案选择

### 方案一：轻量复用现有留言发送能力（推荐）

在右侧新增独立的 `QuickMessageCard`，只承载快速发送职责，复用现有留言发送链路和附件构建逻辑。左侧留言板继续负责完整历史浏览与引用回复。

优点：
- 改动范围小，符合当前需求的“轻量”目标。
- 风险低，不需要拆解现有完整留言板。
- 交互职责清晰：右侧负责快速发，左侧负责完整看。

缺点：
- 页面存在两个留言入口，需要确保发送逻辑一致。

### 方案二：拆分现有留言板为发送区和列表区

将现有 `MessageBoard` 的发送能力抽成通用组件，左右侧统一复用。

优点：
- 结构更整洁，长期更利于演进。

缺点：
- 超出本次轻量目标，容易引入额外重构。

### 方案三：右侧单独实现一套极简发送逻辑

右侧自建发送逻辑，直接构造 message 并写入上下文。

优点：
- 初次开发看起来最快。

缺点：
- 长期容易和左侧发送能力不一致，不推荐。

## 总体设计

### 页面结构

工单详情页保持两栏布局：

- 左侧：工单基本信息 + 完整留言板。
- 右侧：角色操作区 + 快速留言卡片。

右侧采用同一个 `sticky` 容器，内部使用纵向布局：

1. 角色操作区
2. 快速留言卡片

这样可以保证右侧操作与快捷补充留言在同一视线区域内，同时不改变现有主信息阅读路径。

### 组件设计

新增组件：`src/components/TicketDetail/QuickMessageCard.jsx`

组件职责：
- 展示快速留言输入区域。
- 支持文本输入和附件上传。
- 校验空内容发送。
- 调用现有上下文能力追加留言。
- 发送成功后清空输入并显示成功反馈。
- 提供“查看全部留言”入口。

现有组件职责保持：
- `src/components/TicketDetail/MessageBoard.jsx` 继续负责完整留言展示、引用回复、历史浏览。
- `src/pages/TicketDetail/index.jsx` 负责页面编排与滚动锚点连接。

## 数据流设计

### 输入

快速留言卡片接收：
- `ticket`
- `onViewAllMessages`（用于滚动到左侧留言区）

### 发送链路

右侧快速留言发送沿用现有消息结构，但不允许新增一套独立的 message 拼装规则。`MessageBoard` 与 `QuickMessageCard` 必须共用同一个最小发送 helper，确保两个入口的消息结构和发送校验完全一致。

推荐共享一个轻量 helper，例如 `buildMessagePayload(...)` 或 `submitTicketMessage(...)`，覆盖以下公共步骤：

1. 校验发送内容是否为空。
2. 调用 `buildAttachments(fileList, user)` 构建附件对象。
3. 组装统一的 message 对象。
4. 调用 `addMessage(ticket.id, messageItem)` 写入 `ticket.messages`。

右侧 `QuickMessageCard` 仅负责收集输入、触发发送、清理表单和展示反馈，不直接维护独立的消息拼装规则。

统一 message 字段与当前 `MessageBoard` 保持一致：
- `id`
- `authorId`
- `authorName`
- `authorRole`
- `content`
- `contentHtml`
- `attachments`
- `quote`
- `createdAt`

其中右侧快速留言固定写入 `quote: null`。

左侧留言板基于同一数据源自动刷新显示。

### 复用边界

本次不强制抽离整个发送表单组件，但必须抽离最小共享发送逻辑，避免左右两侧在以下规则上发生分叉：
- 空内容校验条件
- 附件构建流程
- message 对象组装规则
- 成功/失败返回约定

不覆盖：
- 左侧引用回复逻辑
- 左侧留言历史渲染
- 左侧富文本编辑器的完整交互

## 交互设计

### 卡片内容

快速留言卡片包含：
- 标题：快速留言
- 精简输入框
- 附件上传按钮
- 主操作按钮：发送按钮
- 次操作按钮：查看全部留言按钮

控件位置要求：
- 发送按钮与附件上传按钮放在输入区下方的操作行内。
- “查看全部留言”使用文本按钮，放在卡片底部或操作行次级位置，不与发送按钮竞争主视觉。

右侧输入区采用纯文本输入，不复用左侧富文本编辑器。为兼容现有消息渲染逻辑，纯文本发送时统一写入：
- `content`：输入框原始文本（去首尾空白后）
- `contentHtml`：空字符串

这样左侧 `RichContentPreview` 会自动走文本回退分支，不引入新的 HTML 生成或转义策略，也避免右侧为了“快速留言”引入富文本复杂度。

### 行为规则

- 用户可发送纯文本。
- 用户可发送仅附件。
- 用户可发送文本 + 附件。
- 文本与附件同时为空时，提示“请输入留言内容或上传附件”。
- 发送中禁用输入与按钮，避免重复提交。
- 发送成功后：
  - 清空输入内容
  - 清空附件列表
  - 停留在右侧卡片
  - 使用 Ant Design 全局消息提示 `message.success('留言已发送')`
- 发送失败后：
  - 保留当前输入内容
  - 保留已选择的附件
  - 恢复可编辑状态
  - 使用 Ant Design 全局消息提示 `message.error('留言发送失败')`
- 不新增独立的成功态页面或内联成功占位，发送完成后表单仍保持可继续输入的默认形态。
- 同时提供“查看全部留言”入口，点击后滚动到左侧留言区。

### 附件规则

右侧快速留言卡片必须继承现有附件上传组件的约束与行为，不单独定义新的附件规则，包括但不限于：
- 文件类型限制
- 文件数量限制
- 文件大小限制
- 重名/重复文件处理方式
- 上传前的本地暂存行为

右侧仅复用现有 `FileUploader`，不新增新的附件处理分支。

### 查看全部留言

左侧完整留言板增加一个固定滚动锚点容器，由详情页在 `MessageBoard` 外层包裹一个带 `ref` 的容器，并作为“查看全部留言”的唯一目标。

右侧点击“查看全部留言”时调用 `scrollIntoView({ behavior: 'smooth', block: 'start' })`，将视口移动到该锚点。

响应式行为要求：
- 桌面双栏布局下，滚动到左侧留言板顶部。
- 移动端单栏堆叠布局下，仍滚动到同一个留言板锚点，即页面中完整留言区的实际位置。
- 不因布局折叠改用其他目标，保证实现和测试口径一致。

## 布局与样式

- 右侧 `sticky` 容器内用 `Space direction="vertical"` 组织角色操作区与快速留言卡片。
- 快速留言卡片宽度与右栏一致。
- 输入区比左侧留言板更紧凑，避免抢占主要操作区空间。
- 移动端下维持现有响应式列堆叠顺序，右侧卡片跟随右栏自然下移。

## 错误处理

- 附件处理失败时提示“留言发送失败”。
- 发送中态结束后恢复可编辑状态。
- 若当前用户信息缺失，则不允许发送；该场景原则上由现有鉴权上下文保障，不额外扩展复杂兜底。

## 影响范围

预计涉及文件：

- `src/pages/TicketDetail/index.jsx`
- `src/components/TicketDetail/QuickMessageCard.jsx`（新增）
- `src/components/TicketDetail/MessageBoard.jsx`（调整为复用共享发送 helper）
- `src/components/TicketDetail/messageComposer.js` 或同等轻量共享 helper（新增）

## 验证方案

至少验证以下场景：

1. 右侧发送纯文本留言成功。
2. 右侧发送仅附件留言成功。
3. 右侧发送文本 + 附件成功。
4. 空文本且无附件时，发送被阻止并给出提示。
5. 发送成功后右侧输入框与附件列表被清空。
6. 左侧完整留言区立即出现新留言。
7. 点击“查看全部留言”后平滑滚动到左侧留言区。
8. 不同角色下，右侧角色操作区与快速留言卡片顺序保持正确。

## 实施建议

先完成最小闭环：

1. 抽取最小共享发送 helper，统一空校验、附件构建和 message 组装。
2. 在详情页右侧接入 `QuickMessageCard`。
3. 打通发送与滚动锚点。
4. 复用现有附件上传与消息追加逻辑完成联调。

这样可以在满足需求的同时，把重构控制在最小必要范围内。
