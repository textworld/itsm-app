# Feature Specification: ITSM 工单原型

**Feature Branch**: `001-itsm-prototype`  
**Created**: 2026-05-19  
**Status**: Draft  
**Input**: 基于当前仓库生成符合 speckit 的 `/specify` 规格内容

## User Scenarios & Testing

### User Story 1 - 提单人提交并跟踪工单 (Priority: P1)

作为提单人，我希望填写问题信息、附件、系统、优先级和联系方式，并将工单提交给技术支持，以便问题能进入人工处理或被 AI 辅助解决。

**Why this priority**: 提单是 ITSM 原型的入口；没有可提交、可追踪的工单，后续受理、派发、排查和关闭流程都无法验证。

**Independent Test**: 使用提单人账号登录，创建草稿，选择“人工处理”后提交，确认工单通过状态机 `SUBMIT` 事件进入待受理状态，并能在提单人列表和详情页看到。

**Acceptance Scenarios**:

1. **Given** 提单人已登录，**When** 填写必填字段并提交人工处理，**Then** 系统创建工单并显示为待受理。
2. **Given** 提单人创建草稿后选择 AI 已解决，**When** 确认解决，**Then** 工单通过状态机关闭并记录 AI 解决信息。
3. **Given** 工单处于待确认状态，**When** 提单人验证通过并提交满意度，**Then** 工单关闭并保留满意度结果。
4. **Given** 工单处于待确认状态，**When** 提单人验证未通过并填写驳回原因，**Then** 工单回到处理中并记录驳回原因。

---

### User Story 2 - 一线支持受理、处理和发起关单 (Priority: P1)

作为一线支持，我希望查看待处理工单、受理工单、补充排查信息、打标缺陷、创建子任务、请求二线支持并发起关单，以便推动问题闭环。

**Why this priority**: 一线支持是主流程的核心处理角色，决定工单是否进入二线、补充信息、挂起、子任务或关单确认。

**Independent Test**: 使用一线支持账号登录，受理待受理工单，执行至少一条有效处理动作，最终在满足规则时发起关单，确认所有状态变化均来自状态机事件。

**Acceptance Scenarios**:

1. **Given** 工单处于待受理，**When** 一线支持点击受理，**Then** 工单进入处理中且处理子状态为一线排查。
2. **Given** 工单处于一线排查，**When** 一线支持请求二线支持，**Then** 工单保持处理中且处理子状态切换为二线排查。
3. **Given** 工单需要提单人补充信息，**When** 一线支持退回补充，**Then** 工单进入信息补充状态。
4. **Given** 工单所有子任务已完成，**When** 一线支持发起关单，**Then** 工单进入待确认状态。

---

### User Story 3 - 二线支持处理二线排查和子任务 (Priority: P1)

作为二线支持，我希望接收一线转入的排查工单或子任务，填写排查结论、处理分派给我的任务，并将结果返回给一线，以便复杂问题能由合适角色处理。

**Why this priority**: 二线支持验证 ITSM 分层处理流程，确保复杂问题不会停留在一线处理视角内。

**Independent Test**: 使用二线支持账号登录，打开二线排查状态工单，填写有效结论并提交一线复核，确认处理子状态回到一线排查。

**Acceptance Scenarios**:

1. **Given** 工单处于二线排查，**When** 二线支持填写排查结论并提交，**Then** 工单回到一线排查。
2. **Given** 子任务分派给二线支持，**When** 二线支持认领、开始并完成子任务，**Then** 子任务关闭并保留处理记录。
3. **Given** 二线支持未填写排查结论，**When** 尝试提交一线复核，**Then** 系统阻止提交并提示前置条件未满足。

---

### User Story 4 - 管理员维护基础配置 (Priority: P2)

作为管理员，我希望维护用户、排班规则、休息时间、险种字典等后台配置，以便原型能演示不同组织、系统和人员配置下的处理体验。

**Why this priority**: 后台配置影响演示数据和业务可用性，但不应直接改变工单生命周期。

**Independent Test**: 使用管理员账号进入后台页面，修改一项配置并保存，确认配置通过共享校验，且不会直接写入工单状态字段。

**Acceptance Scenarios**:

1. **Given** 管理员打开排班配置，**When** 新增或编辑排班规则并保存，**Then** 系统保存配置并通过前后端共享校验。
2. **Given** 管理员打开一线休息时间配置，**When** 添加未来休息时间，**Then** 系统展示未来休息人员清单。
3. **Given** 非管理员访问后台管理页面，**When** 页面加载，**Then** 系统阻止访问或显示无权限状态。

---

### User Story 5 - 用户在列表、详情和留言中协同 (Priority: P2)

作为不同角色的用户，我希望按角色查看工单列表、进入详情页、查看轨迹和留言，并上传或下载附件，以便围绕同一工单完成协同。

**Why this priority**: 列表、详情、留言和附件是工作流可用性的基础，能验证不同角色对同一工单的可见性和操作边界。

**Independent Test**: 分别使用提单人、一线、二线账号登录，确认列表范围、详情操作区、留言和附件行为符合角色权限。

**Acceptance Scenarios**:

1. **Given** 提单人登录，**When** 打开工单列表，**Then** 只看到自己相关的工单。
2. **Given** 一线支持登录，**When** 打开待处理列表，**Then** 能看到可由一线处理的工单和有效操作入口。
3. **Given** 任意参与角色打开工单详情，**When** 添加留言和附件，**Then** 留言保存并能在详情页回显。

### Edge Cases

- 提单人提交缺少必填字段的工单时，系统必须阻止提交并保留已填写内容。
- 无权限角色尝试执行状态机事件时，系统必须拒绝并返回明确错误。
- UI 中可见的操作必须与 API 可执行的操作一致；不得出现 UI 允许但 API 拒绝的正常路径。
- 旧数据中的历史状态必须能归一化为当前工作流状态、双视角状态和处理子状态。
- 工单存在未完成子任务时，一线支持不得发起关单。
- 二线排查未填写结论时，不得返回一线复核。
- 信息补充状态下，提单人修改描述必须保留描述历史。
- 后台配置保存失败时，页面必须保留当前编辑内容并展示错误。
- 上传、导出、重置或本地数据损坏时，系统必须避免静默丢失用户可见数据。

## Requirements

### Functional Requirements

- **FR-001**: 系统必须支持提单人创建草稿、更新草稿、提交工单、AI 确认解决、撤回、补充信息、验证通过、验证驳回和主动关单。
- **FR-002**: 系统必须支持一线支持受理工单、标记缺陷、关联缺陷、更新总结、挂起/恢复、请求二线支持、创建子任务、退回补充信息、发起关单和同角色转派。
- **FR-003**: 系统必须支持二线支持处理二线排查、填写排查结论、认领/转派/处理子任务，并将主工单返回一线排查。
- **FR-004**: 所有工单生命周期状态变更必须通过 `src/state-machine/ticketStateMachine.js` 中的事件流转完成。
- **FR-005**: API、store、视图模型和组件不得直接写入 `status`、`requesterStatus`、`supportStatus` 或 `processingSubStatus`。
- **FR-006**: 系统必须为工单维护面向提单人和技术支持的双视角状态，并在处理中维护有效的处理子状态。
- **FR-007**: 系统必须在状态机流转时记录时间线，包含动作、动作标签、原状态、目标状态、操作人、角色、时间和备注。
- **FR-008**: 系统必须按角色控制列表可见范围、详情页操作区、导航入口和 API 权限。
- **FR-009**: 系统必须支持工单描述的富文本内容、附件、描述历史和信息补充阶段的描述变更记录。
- **FR-010**: 系统必须支持工单留言板，允许相关角色围绕工单追加文本和附件信息。
- **FR-011**: 系统必须支持缺陷打标和缺陷关联，以便一线支持将工单与缺陷数据建立关系。
- **FR-012**: 系统必须支持子任务工单的创建、认领、转派、开始、完成和无需主工单处理的关闭路径。
- **FR-013**: 系统必须支持工单优先级和 SLA 到期时间计算，并在列表和详情中展示必要信息。
- **FR-014**: 系统必须支持用户登录、注册、退出、会话校验和受保护页面访问控制。
- **FR-015**: 系统必须支持管理员维护用户、排班配置、休息时间配置和险种字典配置。
- **FR-016**: 后台配置保存前必须使用共享校验逻辑；前端和后端校验结果必须保持一致。
- **FR-017**: 系统必须支持 SQLite 本地持久化、初始化 mock 数据、导出数据和重置数据。
- **FR-018**: 系统必须在 OpenAI 配置可用时提供 AI 辅助工单描述、AI 草稿解答或关闭总结能力；配置不可用时必须给出可理解提示。
- **FR-019**: 系统必须为状态机、权限、工具函数、路由和关键视图行为提供聚焦测试。
- **FR-020**: 新增或修改工作流行为时，必须覆盖至少一个成功路径和一个关键失败或无权限路径。

### Key Entities

- **Ticket**: 工单主实体，包含标题、描述、富文本描述、附件、提单人、优先级、系统、状态、双视角状态、处理子状态、时间线、留言、缺陷信息、总结、满意度和关闭信息。
- **State Transition**: 状态机流转规则，包含来源状态、事件、目标状态、角色、守卫条件、转换逻辑和时间线记录策略。
- **User**: 系统用户，包含账号、名称、角色和可访问能力；核心角色包括提单人、一线支持、二线支持和管理员。
- **Message**: 工单协同留言，包含作者、内容、附件和创建时间。
- **Attachment**: 附件实体，支持上传、保存、回显和下载。
- **Defect**: 缺陷记录，用于被工单标记或关联。
- **Subtask Ticket**: 子任务工单，与主工单关联，有独立的处理状态、处理人和关闭路径。
- **Schedule Config**: 后台排班配置，包含系统范围、基础排班人员、险种排班小组和灵活规则。
- **Support Rest Config**: 一线支持休息时间配置，包含人员、日期、时段和未来清单展示。
- **Insurance Dictionary**: 险种字典配置，用于后台维护可用险种。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 提单人能在 3 分钟内完成一张包含描述、系统、优先级和附件的工单提交，并在列表中看到该工单。
- **SC-002**: 一线支持能从待受理到待确认完成一条标准处理链路，且每一步状态变化都能在工单时间线中追溯。
- **SC-003**: 二线支持能完成二线排查并返回一线，未填写结论时系统必须阻止提交。
- **SC-004**: 任一角色尝试执行无权限状态流转时，API 返回失败，且不会产生状态字段变更。
- **SC-005**: 管理员保存后台配置时，非法配置会被前端或后端校验阻止，并展示可理解的错误。
- **SC-006**: 关键测试覆盖状态机主路径、权限矩阵、后台配置校验、工单列表过滤、关键路由和核心视图操作。
- **SC-007**: 导出和重置数据操作不会破坏运行时数据库结构，初始化后能恢复可演示数据。

## Assumptions

- 本规格描述的是当前 ITSM 原型的目标行为和约束，不代表生产级多租户、审计合规、权限平台或高可用部署范围。
- SQLite、本地上传目录、mock 数据和演示账号是当前原型的默认运行方式。
- 后台排班、休息时间和字典配置主要用于演示与配置维护；除非另有规格明确说明，否则不改变工单状态机和自动派单逻辑。
- AI 能力依赖服务端环境变量配置；AI 不可用时，核心人工工单流程仍必须可用。
- 旧状态数据需要兼容读取和归一化，但新增业务状态应优先通过当前状态机模型表达。

## Constitution Compliance

- 工单状态变更必须通过状态机事件完成，尤其是 `SUBMIT`、`ACCEPT`、`REQUEST_L2_SUPPORT`、`L1_REVIEW`、`INITIATE_CLOSURE`、`VERIFY_YES` 和 `VERIFY_NO` 等事件。
- 不允许在接口、store 或组件中直接写入 `status`、`requesterStatus`、`supportStatus`、`processingSubStatus`。
- 角色权限必须在 UI 和 API 之间保持一致。
- 后台配置与工单生命周期默认分离；若要接入派单或状态变化，必须先补充状态机事件或明确的派单规格。
- 所有新增行为必须提供对应测试或说明无法测试的原因。
