# ITSM Spring Boot 微服务项目宪章

## 核心原则

### I. 单体微服务内必须保持 DDD 边界

本项目是一个正式的 Spring Boot 后端微服务。部署形态可以是单个服务，但代码、模型、数据和依赖必须按照 DDD 限界上下文组织，不能因为当前是单服务而跨领域直接调用、直接查表或共享内部模型。

必须至少保持以下领域边界：

- `auth`：统一身份、外部账号绑定、登录会话、角色上下文。
- `ticket`：工单聚合、生命周期状态机、留言、附件引用、处理轨迹、指派关系。
- `config`：业务系统配置、字典、字段映射、展示配置。
- `integration`：Sofa、钉钉、系统 A、系统 B、OA 等外部平台适配。
- `shared`：通用异常、返回值、ID、时间、分页、领域事件基类等无业务归属能力。

领域之间只能通过应用服务接口、领域事件、查询模型或防腐层端口交互。禁止一个领域直接依赖另一个领域的 repository、JPA entity、mapper、数据库表结构或外部平台 DTO。

理由：当前选择一个微服务承接，是为了降低部署复杂度，不是放弃领域边界。只有在单服务内保持清晰边界，后续才有依据拆分为独立微服务。

### II. 工单生命周期唯一由状态机驱动

所有涉及工单生命周期的写操作，必须通过 `ticket` 领域的命令处理链进入状态机或领域服务。任何 Controller、Application Service、Repository、Mapper、SQL、前端页面都不得直接写入工单的 `status`、`requesterStatus`、`supportStatus`、`processingSubStatus` 等生命周期字段。

工单创建同样属于生命周期事件。新建工单必须进入领域模型，并通过明确的 `SUBMIT` 等业务事件进入状态流转。若需要新增编辑、审批、撤回、补充、关闭、重新打开等能力，必须先补充状态机事件、守卫条件、状态迁移和测试，再接入接口与界面。

理由：工单系统的核心一致性来自状态机。绕过状态机直接落库会破坏权限、审计、轨迹和历史语义。

### III. 数据所有权与仓储边界必须可拆分

每张业务表必须有且只有一个领域 owner。拥有者负责表结构、写入规则、数据迁移和业务解释。其他领域不得直接写入，也不得通过自己的 repository 读取对方主表。

推荐数据归属如下：

- `auth_*`：由 `auth` 领域拥有，包括身份主体、外部身份绑定、登录会话。
- `ticket_*`：由 `ticket` 领域拥有，包括工单主表、状态历史、留言、附件引用、OA 申请快照。
- `config_*`：由 `config` 领域拥有，包括系统配置、字典、字典项、字段映射。
- `integration_*`：由 `integration` 领域拥有，包括外部调用日志、回调记录、重试记录、幂等记录。
- `outbox_*`：由发布事件的领域拥有，或由基础设施统一实现但按领域区分事件 owner。

跨领域读数据时，优先使用查询接口、领域事件投影、只读视图或快照字段。禁止为了页面展示而在业务写路径中跨领域 join 主表。

理由：数据所有权是后续拆分数据库和微服务的最低成本路径。没有表 owner，就没有可靠的服务边界。

### IV. 身份、角色与外部账号必须分离

系统内部只认统一身份主体 `principal`。外部账号只作为身份来源和绑定信息存在，不得直接成为工单、审批、处理、审计的主身份。

必须支持以下身份接入方式：

- 提单人 Web：通过 Sofa 网关外部登录授权获得系统 A 账号，再映射为内部 `principal`。
- 提单人移动端：通过钉钉登录体系获取 `userid`，再调用系统 A 接口换取系统 A 账号，最后映射为内部 `principal`。
- 处理人 Web：读取页面 cookie 后调用系统 B 接口获取当前登录人账号，再映射为内部 `principal`。

角色必须作为业务上下文计算，例如 `REQUESTER`、`L1`、`L2`、`ADMIN`。同一 `principal` 可以绑定多个外部账号，也可以在不同场景拥有不同角色上下文。

理由：登录来源、外部账号和业务角色是三个不同概念。混在一起会导致权限、审计、多端访问和账号合并不可控。

### V. 外部平台访问必须经防腐层

所有 Sofa、钉钉、系统 A、系统 B、OA 的访问都必须通过 `integration` 领域的适配器完成。业务领域只能依赖内部端口或应用服务，不能直接拼接 HTTP 请求、读取外部 cookie、解析外部响应结构或使用外部系统状态码。

外部平台返回值必须转换为内部模型后再进入领域流程。OA 审批结果不得直接修改工单状态，必须先落入内部审批结果模型或 OA 快照，再通过工单领域命令或领域事件触发状态机。

每个外部适配器必须定义：

- 调用目的和业务 owner。
- 请求参数与响应模型。
- 超时、重试、幂等策略。
- 错误码映射。
- 日志脱敏规则。
- 契约测试或适配器测试。

理由：外部系统变化不可控。防腐层可以把协议、认证、错误码和数据结构变化限制在集成边界内。

### VI. 历史快照、审计与可观测性必须保留

所有会影响历史解释和审计的业务信息，必须在写入时保存快照，不能只依赖实时关联查询。至少包括：

- 提单人、处理人、审批人的名称快照。
- 系统编码、系统名称、字段名称快照。
- 字典编码、字典项编码、字典项中文名快照。
- OA 申请号、流程实例号、审批节点、审批结果、审批意见、审批时间快照。
- 状态迁移前后状态、触发事件、操作人、操作时间、请求摘要。

正式系统必须保留关键操作审计日志和外部调用日志。日志中不得泄露敏感 token、cookie、手机号、身份证号等敏感信息；确需记录时必须脱敏。

理由：ITSM 工单是带时间上下文的业务证据。正式系统必须能回答谁在什么时候基于什么外部结果改变了工单。

### VII. 测试与迁移必须守护领域规则

新增或修改业务时，必须补充与风险匹配的测试。状态机使用领域单元测试，应用服务使用用例测试，外部平台使用契约或适配器测试，接口层使用 Controller/API 测试，数据库结构使用迁移验证。

凡是影响以下内容的变更，必须至少覆盖一个成功路径和一个关键失败路径：

- 工单生命周期
- 身份映射
- 角色权限
- OA 审批结果处理
- 数据所有权
- 外部平台调用
- 字典和配置解释

数据库结构必须通过 Flyway、Liquibase 或等价迁移机制管理。禁止手工修改生产表结构后再补代码。

理由：正式系统的可维护性来自可重复验证。测试和迁移是防止领域规则被后续实现绕开的门禁。

## 正式系统定位

本项目面向正式的 Spring Boot ITSM 微服务开发，不以 demo、mock 或临时页面作为架构例外。可以保留演示数据或模拟适配器用于本地开发，但它们必须被明确隔离在测试、开发环境或 mock adapter 中，不能进入正式业务路径。

系统必须稳定承接：

- 提单人通过系统 A 身份访问 Web 提单页面。
- 提单人通过移动端钉钉登录后换取系统 A 身份并访问提单、工单详情。
- 处理人通过系统 B 登录态访问处理页面。
- OA 审批流程结果回写并驱动工单状态流转。
- 系统配置和字典配置驱动工单字段展示和历史快照。

## Spring Boot 技术边界

推荐采用单仓库、多 Maven/Gradle 模块结构：

- `itsm-bootstrap`：启动类、配置装配、运行时 profile。
- `itsm-interface`：Controller、DTO、请求校验、接口 assembler、安全入口。
- `itsm-application`：用例编排、事务边界、命令处理、查询编排。
- `itsm-domain`：聚合根、实体、值对象、领域服务、状态机、领域事件、repository 端口。
- `itsm-infrastructure`：JPA/MyBatis 实现、外部客户端、消息、缓存、文件存储、repository 实现。
- `itsm-shared`：无业务归属的通用工具和基础类型。

依赖方向必须单向：

`interface -> application -> domain`

`infrastructure` 可以实现 `domain` 或 `application` 定义的端口，但领域层不得依赖基础设施层。领域模型不得依赖 Spring Web、JPA Entity、MyBatis Mapper、HTTP Client 或外部平台 SDK。

事务边界原则上放在应用服务。领域对象表达业务规则，基础设施只负责持久化和技术适配。

## 数据治理

所有数据表设计必须在规格或计划中声明：

- 表名和 owner 领域。
- 是否属于聚合内部表。
- 是否允许其他领域读取。
- 是否需要快照字段。
- 是否需要审计、幂等、软删除或版本号。
- 迁移脚本名称和回滚策略。

正式业务写路径不得跨领域 join 后决定状态变更。若确需跨领域信息，必须通过应用服务查询、领域事件投影或写入时快照解决。

## 交付工作流

任何新功能必须按以下顺序推进：

1. 确认影响的限界上下文、聚合、命令、事件和数据表 owner。
2. 明确是否影响工单生命周期、身份映射、OA 流程、外部平台适配或配置解释。
3. 先设计领域模型和状态机，再设计应用服务，再设计接口 DTO 和基础设施实现。
4. 新增外部平台交互时，先定义端口、适配器、错误映射和日志策略，再接入业务流。
5. 新增数据表时，先确认 owner 和迁移脚本，再实现 repository。
6. 提交前运行相关测试；无法运行时必须说明原因和风险。

规格、计划和任务必须显式标注是否触及：

- `ticket` 状态机和生命周期字段。
- `auth` 身份映射与角色上下文。
- `integration` 外部系统适配器。
- `config` 字典、系统配置或字段映射。
- 数据库迁移脚本。
- 跨领域查询或投影。

## 治理

本宪章约束正式 Spring Boot 微服务的所有规格、计划、任务和实现。任何与本宪章冲突的设计，必须先修改设计；若确需偏离，必须在规格中明确说明偏离范围、原因、风险和退出方案。

修订要求：

1. 说明变更原因。
2. 说明受影响的原则、领域边界和数据表 owner。
3. 根据语义判断版本号：
   - MAJOR：修改核心领域原则、数据所有权原则或状态机总原则。
   - MINOR：新增领域约束、技术边界、交互边界或治理规则。
   - PATCH：只修正文案或澄清措辞。
4. 同步审查受影响的规格、计划、任务、模板和迁移约定。

合规审查必须在规格阶段、计划阶段和实现完成前执行。最低检查项包括：

- 工单状态是否只通过状态机变更。
- 是否存在跨领域直接写表或直接依赖 repository。
- 身份是否统一映射到 `principal`。
- 外部平台是否都经 `integration` 防腐层访问。
- 历史数据是否保留必要快照。
- 数据表是否有唯一 owner。
- 数据库迁移和测试是否覆盖关键路径。
