# ITSM 应用原型宪章

## 核心原则

### I. 状态机拥有工单生命周期

所有涉及工单生命周期状态的业务变更，必须表达为由
`src/state-machine/ticketStateMachine.js` 处理的事件。工单创建同样属于状态机流转，除非明确通过状态机创建草稿，否则必须通过 `SUBMIT` 事件进入工作流。

API、store、视图模型和 React 组件不得直接赋值或持久化
`status`、`requesterStatus`、`supportStatus` 或 `processingSubStatus`。任何影响生命周期行为的新工单编辑能力，必须先新增或扩展状态机事件、守卫条件和转换逻辑，再把该事件接入 API 和界面。

理由：该原型用于展示 ITSM 工作流。状态机是生命周期规则、双视角状态投影、子状态归一化、时间线创建和流转权限检查的唯一事实来源。

### II. 角色感知的工作流完整性

所有面向用户的操作都必须受角色、工单状态和工作流上下文约束。提单人、一线支持、二线支持和管理员的体验，只能暴露该角色在当前状态下有效的操作。

权限应通过状态机角色权限、`src/permissions/ticketPermissionMatrix.js`、路由保护或共享纯函数集中管理。页面组件中的重复临时权限判断，只能作为展示保护，并且必须与集中规则保持一致。

理由：列表过滤、详情操作、导航入口和 API 路由必须描述同一套工作流。界面上出现但服务端失败的按钮，或者绕过界面规则的 API 操作，都是产品缺陷。

### III. 原型范围必须明确

每个功能规格必须说明目标、非目标、受影响角色、受影响路由，以及该功能是否改变工单派发、人员分配、工单状态、持久化或后台配置。仅用于原型的行为、mock 数据、演示账号、AI 辅助流程和人工后台配置，必须明确标注为原型能力。

功能应优先选择狭窄、可演示的工作流增量，而不是宽泛的平台基础设施。若某个功能不需要改变派发或工单生命周期，必须明确说明这些行为保持不变。

理由：本仓库是用于验证 ITSM 工作流的可运行原型。清晰的范围可以防止配置页面、mock 便利能力和 AI 助手静默演变成生命周期规则。

### IV. 数据与配置必须可审计

影响业务工作流的工单变更，必须通过状态机时间线、更新时间戳、操作人身份和相关领域字段留下审计轨迹。描述变更必须保留描述历史。后台配置变更在持久化前必须使用共享校验。

运行时数据本地存储在 SQLite 和 `data/` 下的上传目录中；任何涉及持久化的实现计划，都必须考虑初始化、导出/重置行为、备份预期，以及与现有 mock 数据或 fallback 数据的兼容性。

理由：即使作为原型，该应用也在建模真实运维工作。系统必须清楚呈现谁改了什么、何时修改，以及哪些规则接受了该变更。

### V. 测试守护行为

任何行为变更都必须在最低可行层级补充聚焦测试：生命周期规则使用状态机测试，过滤/校验使用纯工具函数测试，服务端契约使用路由测试，用户可见行为使用组件或视图测试。

修改工作流、角色可见性、持久化或配置校验时，测试必须至少覆盖一个成功路径，以及最重要的非法路径或无权限路径。现有测试必须保持有意义；不得为了让变更通过而删除或削弱测试，除非有明确的替代测试。

理由：该仓库已经依赖纯函数测试和路由/视图测试来保持原型行为稳定。没有测试的新工作流行为会让后续迭代变得不安全。

## 产品上下文

该应用是一个基于 Next.js、React、Ant Design 和 SQLite 构建的 ITSM 工单原型。它支持提单人提交、AI 辅助草稿解决、一线受理与排查、二线支持、子任务、信息补充、关单确认、满意度收集、留言板、附件、排班配置、一线休息时间配置、用户管理和险种字典配置。

产品优先保证工作流清晰，而不是追求生产级平台广度。演示账号、mock 种子数据、本地持久化和后台配置页面都是有效的原型工具，但它们不得绕过上述工作流原则。

## 技术边界

应用在 `app/` 下使用 Next.js App Router，在 `src/server/` 下放置共享服务端模块，在 `src/views/` 和 `src/components/` 下放置 React 视图与组件，并在 `src/state-machine/`、`src/permissions/`、`src/utils/` 和 `src/constants/` 下放置共享领域逻辑。

新增工作应遵循现有模块边界：

- Route Handler 负责校验会话、角色、请求形状，并调用共享服务端或领域 helper。
- 组件负责渲染工作流状态并分发用户意图；组件不拥有业务生命周期规则。
- 共享 helper 承载确定性的转换、过滤、格式化和校验逻辑，并且应能脱离浏览器测试。
- 除非规格明确引入状态机事件或派发集成，否则后台配置应与工单状态保持分离。

## 交付工作流

对于非平凡变更，必须先编写规格再实现。规格必须包含业务上下文、目标、非目标、用户流程、数据/API 变更、权限规则、错误处理、测试策略和风险。通过文档化设计会话推进的工作，应把提示词和设计记录保存在 `docs/superpowers/prompts/` 和 `docs/superpowers/specs/` 下。

实现计划必须标明变更是否触及：

- `src/state-machine/ticketStateMachine.js`
- 工单状态字段或时间线行为
- `app/api/` 下的 Route Handler
- `src/server/` 或 `src/context/` 下的 store
- 角色权限或受保护导航
- SQLite schema、种子数据、导出/重置行为或上传
- 后台配置校验

验证时必须运行相关测试；若无法运行，必须说明原因。

## 治理

本宪章约束该仓库未来所有规格、计划、任务和实现工作。当拟议变更与本宪章冲突时，必须重新设计该变更，或先修订本宪章。

修订要求：

1. 说明清晰的变更原因。
2. 更新受影响的原则或章节。
3. 按语义化版本规则提升版本号：
   - MAJOR：移除或重新定义原则。
   - MINOR：新增原则或实质性扩展治理规则。
   - PATCH：不改变义务的澄清说明。
4. 审查受影响的规格、计划和模板。

合规审查必须在规格评审期间进行，并在实现被认为完成之前再次进行。最重要的合规检查包括：状态机之外不得直接写入工单状态；角色/状态权限在 UI 和 API 之间保持一致；原型范围明确；审计数据被保留；相关测试已经运行。
